# 毕业论文参考文献工作方案

> 适用对象：本仓库的 ATS 招聘管理系统（FastAPI + Vue 3 + MySQL，见根目录 README）
>
> 用途：把「自己实习里做的东西」变成一篇经得起查、经得起答辩问的毕业论文

---

## 0. 先纠正一个常见误解

「项目是我自己在实习里从零做的」和「需不需要参考文献」是两件不相干的事。

毕设的评分点从来不是「你有没有抄别人的代码」，而是：

1. 你知不知道自己做的这件事，**别人已经做到什么程度**（背景与意义）；
2. 你的技术选型和实现方法，**依据是什么**（合理性与专业性）；
3. 你的结论，**能不能被别人的工作印证或对比**（可信度）。

所以自研项目不但可以有参考文献，而且**必须**有——恰恰因为你没有现成论文可抄，导师和答辩老师更会通过参考文献来判断你是不是真的懂这个领域。

**参考文献不需要「和你做的系统一模一样」**。一篇讲 Transformer 的论文，和你写的招聘系统毫无关系，但它支撑了你「为什么用大模型做简历筛选」这一句，它就是合规的参考文献。

## 1. 你这个项目该有哪几类文献（配比建议）

本科毕设一般要求 **15～30 篇**，其中外文 2～5 篇。按你的技术栈，建议这样配：

| 类别 | 在论文里干什么 | 主要落在哪一章 | 建议篇数 |
| :--- | :--- | :--- | :--- |
| 中文期刊论文 | 说明「招聘 / 简历筛选 / HR 信息化」这个方向已有研究，你的问题有普遍性 | 第 1 章 绪论、第 2 章 相关技术 | 5～7 |
| 学位论文（硕士为主） | 同方向系统的设计与实现参考，论证你的架构与模块划分合理 | 第 2 章、第 4 章 系统设计 | 2～4 |
| 专著 / 教材 | 软件工程方法、数据库设计、机器学习基础等通用理论 | 第 1～4 章 | 3～4 |
| 标准与规范 | 需求规格、文档编制、软件质量与测试的写法依据 | 第 3 章 需求分析、第 6 章 测试 | 2～3 |
| 外文文献（期刊 / 会议） | LLM、信息抽取、Web 架构等关键技术的方法溯源 | 第 2 章、第 5 章 详细实现 | 3～5 |
| 电子资源（官方文档） | 具体框架、库、协议的确切用法依据 | 第 2 章、第 5 章 | 4～6 |

> **关键提醒**：官方文档类**不能超过总数的三成**。全是 `fastapi.tiangolo.com` 这种，会被批「缺乏学术性」。学位论文是最容易被本科毕设忽略、又最容易找、导师也最认可的一类。

## 3. 必须你自己检索补全的部分（我不会替你编造）

上表中没有**中文期刊论文**和**同方向学位论文**——因为这两类我无法保证题名、作者、年期、页码的真实性，而**编造文献是学术不端里最容易被抓的一种**（答辩老师随手一查就露）。这类必须你自己在知网检索后导出。

好在它们极其好找。建议检索式：

| 找什么 | 知网 / 万方检索式 | 大概能找到 |
| :--- | :--- | :--- |
| 招聘管理系统 | 主题 = ("招聘管理系统" + "招聘流程") AND 年 = 2019—2025 | 大量硕士学位论文，可直接引 1～2 篇做架构参考 |
| 简历筛选 / 简历解析 | 主题 = ("简历筛选" OR "简历解析" OR "人才筛选") | 中文期刊若干，撑第 1 章背景 |
| AI 辅助招聘 | 主题 = ("人工智能" + "招聘") OR ("大语言模型" + "人力资源") | 近三年的综述或应用类文章，撑「研究现状」 |
| 前后端分离 | 主题 = ("前后端分离" AND "Web") | 技术类期刊与学位论文很多 |
| 状态机 / 业务流程 | 主题 = ("有限状态机" AND ("业务流程" OR "状态流转")) | 支撑你 7 阶段管线状态机的设计依据 |
| 信息抽取 | 主题 = ("信息抽取" + "大语言模型") OR ("提示词工程") | 支撑 AI 筛选模块的方法 |

**选文献的三条硬标准**（我自己检索时要过的筛子）：

1. **能读到全文**（至少能读到摘要和结论），否则你写不出「它说了什么」；
2. **能在正文找到一句话用上它**，否则不列；
3. 优先 **近 5 年 + 被引次数高 + 发表在正规期刊/学位论文库**。

一个更省事的办法：**顺藤摸瓜**。找到 1 篇同方向的硕士学位论文，直接看它的参考文献表，顺着它的引用再挑 3～5 篇你自己核实过的。这是所有做毕设的人都在用的合法路径，比自己瞎搜快十倍。

## 4. 「实习里做的」这部分怎么处理

这里有个真实的坑：**实习经历不是文献，内部资料也不能进参考文献**。正确写法是把它放进「研究背景」和「致谢」，而不是放进文献表。

### 4.1 在正文里这样表述

> 本课题来源于作者在某互联网公司招聘团队的实习实践。实习期间作者观察到：招聘专员需在多个 Excel 与邮件之间反复核对候选人状态，7 个面试环节的推进信息分散、缺乏统一视图，人工汇总周报平均耗时数小时。为改善这一流程，作者设计并实现了本系统……

- **公司名脱敏**：写「某互联网公司」「某企业」，除非导师明确允许写实名。
- **数据脱敏**：论文里出现的候选人姓名、简历、面试评价，全部用虚构样例；仓库 README 里也写了「含个人隐私的材料不入库」，论文同理。
- **公司内部文档**（流程规范、内部平台设计稿）**一律不列入参考文献**，也不能大段引用。你在正文里写「结合作者在实习中了解到的招聘流程」，属于自述实践，不构成引用。
- 如果确实需要由公开资料支撑「行业普遍存在这个痛点」，引**公开的行业报告或期刊论文**，而不要引内部资料。

### 4.2 在致谢里写清楚

致谢部分说明「本系统的需求来源于作者在 XX 公司的实习实践」，既诚实，又解释了为什么选题落地性强——这是加分项，不是减分项。

## 5. 边写边引的流程（别等到最后凑）

1. **先定目录**：按学校模板把一、二、三级标题列出来，写到能看出「每一节要论证什么」。
2. **标需求点**：在每节下面用括号写「此处需要依据：行业现状 / 技术原理 / 标准规范」。
3. **按需检索**：一次只解决一个需求点，找到就导出，找不到就换个关键词——不要先攒一堆文献再想往哪塞。
4. **边写边插**：正文写到哪、引到哪，立刻在句末标 `[n]`。Word 里用「引用 → 交叉引用」或 Zotero 插件维护编号，正文一改自动重排。
5. **最后收尾**：全部写完后，从头扫一遍——每个 `[n]` 都要在文献表里有对应条目，每条文献都要在正文出现过至少一次。**有文献没被引用，或引用了却查不到条目，都是明确的扣分点。**

工具建议：知网/万方导出 → 选 GB/T 7714—2015 格式 → 存进 Zotero（或 NoteExpress）→ Word 插件一键生成文献表，格式不会错。

### 一条自查口诀

> **每一项都对得上，每一条都读得到，每一篇都引过。**

## 7. 答辩与查重的避坑清单

| 坑 | 后果 | 怎么躲 |
| :--- | :--- | :--- |
| 参考文献全是官方文档 | 被批「没有学术性」「这不是文献综述」 | 官方文档控制在 1/3 以内，补齐期刊与学位论文 |
| 引了但正文没标 `[n]` | 老师问「这篇你哪儿用的」直接哑火 | 每条文献至少对应正文一处标注 |
| 正文标了但文献表里没有 | 格式错误，直接扣分 | 最后统一用工具重排编号，别手改 |
| 编造文献 | **学术不端**，最重的处罚 | 只列能读到全文的；不确定就换一篇 |
| 页码/年份/出版社写错 | 老师随手一翻就露 | 导出时按数据库元数据核对，别手打 |
| 直接抄别人的文献表 | 里面混进与本文无关的文献 | 手抄一条就要读一条 |
| 把公司内部资料当文献 | 保密问题 + 引用不成立 | 内部资料只在正文自述，不进文献表 |
| 中文文献一条外文都没有 | 不符合多数学校的硬性要求 | 至少 2～5 篇外文，本文第 2.3、2.4 节已够 |

关于查重：绝大多数学校的查重系统**排除参考文献列表**，所以文献多不会推高重复率；真正会推高重复率的是技术介绍章节里大段抄文档原文——这部分要**用自己的话重写**，而不是靠少列文献来规避。
