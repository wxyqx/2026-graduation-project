## 0. 这份文档怎么用

### 0.1 三道闸门

毕设不是「一直写」，而是**反复过三道闸**。每一章都必须过完三道才能进下一章：

| 闸门 | 要问的问题 | 不过的典型症状 | 修法 |
| :--- | :--- | :--- | :--- |
| **论点闸** | 这一章在证明什么？能对应到哪个研究问题？ | 通篇都是「我实现了 X」，没有主张 | 回到第 1 节写 RQ，每节开头先写一句论点 |
| **证据闸** | 这个主张的证据是什么？代码？数据？测试？文献？ | 「性能良好」「界面美观」这类无证据形容 | 换成数字、截图、对照表、引用 |
| **表达闸** | 读者不看代码能不能看懂？图和表是否自解释？ | 大段贴代码、图没图注、术语前后不一 | 按第 5 节图表规范改 |

### 0.2 三个产出物（贯穿全程）

1. **论文正文**（Word，按学校模板）
2. **图表源文件**（draw.io / PlantUML / PowerDesigner / 截图，每张图一个源文件，能改）
3. **证据包**（测试用例表、评估数据表、git 提交统计、设计文档版本链）——答辩时最硬的底牌

## 1. 先确定「你在研究什么」

### 1.1 本科毕设的三种死法

| 死法 | 长相 | 你的风险 |
| :--- | :--- | :--- |
| **工程报告化** | 全篇「我做了登录页、我做了列表页、我做了导出」，老师问「你的研究问题是什么」答不上来 | **高风险**——你的 README 就是功能清单式的 |
| **文档翻译化** | 第 2 章把 FastAPI 官网、Vue 官网翻译一遍 | **高风险**——你的技术栈正是热门框架 |
| **功能清单化** | 用「功能点数量」当工作量，用「界面截图」当成果 | 中风险——你有 7 个页面，很容易写成这样 |

**根因**：把「系统」当成了目的。系统只是**论据**，论文的论点是「某种做法在这个约束下是可行的/更优的」。

### 1.2 问题重述法：从「做个系统」到三个研究问题

把「我要做一个招聘管理系统」改写成下面三句话，你就有论文了：

> **RQ1（建模问题）**
> 在多阶段、可撤回、人工与 AI 混合决策的招聘流程中，如何用状态机建模，才能保证流程数据的一致性与可回溯性？
>
> **RQ2（方法问题）**
> 在「单用户自用、无标注语料、需快速迭代」的约束下，通用大语言模型配合结构化约束提示词，能在多大程度上替代人工完成简历初筛？其结论与人工判断的一致性如何度量？
>
> **RQ3（数据组织问题）**
> 多岗位 × 多阶段的交叉统计，如何在「暂停招聘、淘汰、撤回、时间范围」等边界条件下保持口径一致，并支持逐格下钻与可复现导出？

这三条不是硬套的，它们恰好对应你系统里**最难、最值得写的三块**：

| RQ | 对应系统模块 | 你的原始素材 |
| :--- | :--- | :--- |
| RQ1 | 7 阶段 advance/revert 状态机、overall_status | `招聘流程状态流转表.html`、`services/状态机` 代码 |
| RQ2 | AI 录入管线：PyMuPDF → LLM → 解析容错 → 多配置轮询 | `routers/ai_screen.py`、`services/` 提示词与解析 |
| RQ3 | 阶段×岗位交叉表、格子下钻、三模式导出 | `/api/stats/matrix`、`/api/export` |

### 1.3 贡献声明（写进摘要和 1.3 节，三条就够）

模板句式：

> 本文的主要工作包括：
> （1）**方法/模型类**：提出了一种支持逆向转移的 7 阶段招聘流程状态机，明确了「推进—淘汰—撤回—复活」的转移不变量，解决了…
> （2）**技术/系统类**：设计并实现了零训练成本的简历初筛方法——「锁定 JSON 契约 + 多配置轮询 + 多形态解析容错」，在不更新任何模型参数的前提下…
> （3）**评估类**：构建了含 N 份标注简历的评估集，从准确率、F1、与人工判断一致性、稳定性、时延五个维度给出量化结果，并完成消融对比。

> **注意**（3）是你现在**完全没有**的东西，也是唯一能让你从「做了个系统」跨到「做了项研究」的东西。第 3 节专门讲怎么补。

### 1.4 一条贯穿全文的自检

每写完一节，问一句：**「这一节在证明哪个 RQ？」**
答不上来的段落，要么删，要么降级为附录。

## 2. 技术选型的方法论

「我用了 FastAPI」不是学术内容；「我为什么用 FastAPI、放弃了什么、代价怎么补」才是。

### 2.1 四步决策法

1. **列候选**：至少 2 个真实候选（不能只写一个然后夸它）
2. **定维度**：从**本项目约束**出发的维度，而不是通用维度
3. **打分/对比**：能定量就定量（启动时间、依赖体积、代码量），不能定量就定性质
4. **写取舍**：明确写出「放弃了什么」和「代价怎么补偿」——这一步是老师判断你有没有独立思考的关键

### 2.2 本项目可直接用的四张选型表

**表 2-1 后端框架**

| 维度 | FastAPI | Django REST | Flask |
| :--- | :--- | :--- | :--- |
| 异步支持 | 原生 async/await | 有限（需 ASGI 适配） | 需扩展 |
| 与 LLM 流式/并发调用的契合度 | 高（`asyncio` + httpx 并发，直接服务 AI 录入场景） | 中 | 中 |
| 自动接口文档 | 内置 OpenAPI（`/docs` 即接口清单，本项目 30 个接口全部有中文说明） | 需 drf-spectacular | 需扩展 |
| 数据校验 | Pydantic 模型即 schema | Serializer | 无内置 |
| 代价 | 生态不如 Django 全，ORM 需另配 | 更重、异步弱 | 更自由但样板代码多 |

**表 2-2 前端框架**（Vue 3 vs React vs 服务端渲染模板）

**表 2-3 数据库**（MySQL 8 vs SQLite vs PostgreSQL）——关键论点：本项目是**本地自用**，SQLite 其实更轻，但你选了 MySQL 是为了…（如：与实习环境一致、需要 utf8mb4 中文全文、便于用 Navicat 查看）。**诚实写出这个取舍，比硬夸 MySQL 好**。

**表 2-4 LLM 调用方式**（本表最重要）

| 方案 | 训练成本 | 数据需求 | 准确性 | 迭代速度 | 本项目适用性 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 自训练分类模型 | 高 | 需数百份标注简历 | 领域内可高 | 慢 | ✗ 无标注语料 |
| 微调开源模型 | 中高 | 需标注 + 算力 | 较高 | 中 | ✗ 单机环境 |
| **通用 LLM + 约束提示词（本文）** | **零** | **零** | **依赖提示词质量，需约束** | **改提示词即迭代** | **✓** |

→ 这里的论证依据就引 **GPT-3 少样本学习**那一篇（清单第 16 条）：它证明了「不更新参数、仅通过上下文示例与指令即可完成新任务」。你不是偷懒，你是选了有文献支持的技术路线。

### 2.3 写作句式（直接抄）

- **选型**：「本系统选用 X 而非 Y，基于三点考虑：其一，〔本项目约束，如单机部署、无运维〕；其二，〔技术事实，如原生异步支持，可并发调用外部 API〕；其三，〔生态与可维护性〕。其代价是〔如生态不如 Y 完整〕，本系统通过〔补偿措施〕予以弥补。」
- **现状综述**：「A 等[3]采用……，提升了……，但其局限在于……；B 等[5]在此基础上引入……；然而上述工作均未考虑……，这正是本文的切入点。」
- **局限**：「本方法的局限在于〔场景〕下会〔失效表现〕，后续可通过〔具体改进〕缓解。」

**反面示例**（千万别写）：「FastAPI 是一个高性能的 Python Web 框架，具有很多优点。」

## 3. 评估方法论（你现在最缺的一块）

一句话原则：**没有量化评估的毕设，天花板就是「及格」；有量化评估的毕设，才可能「良好」以上。**

### 3.1 三级验证体系

| 级别 | 验证什么 | 方法 | 产出物 |
| :--- | :--- | :--- | :--- |
| **L1 功能正确性** | 状态机不变量是否恒成立 | 不变量列表 + 边界用例 | 不变量表、边界用例表 |
| **L2 接口契约** | 每个接口的输入输出与错误码 | 已有 `smoke_test.py`（72 项断言）整理成用例表 | 测试用例表（约 40 行） |
| **L3 效果评估** | AI 筛选到底准不准 | 标注集 + 指标 + 消融 | 混淆矩阵、指标表、消融对比图 |

### 3.2 L1：把状态机写成「不变量」——这是论文里最像研究的一段

不要描述代码，而是**声明不变量并验证**：

| 编号 | 不变量 | 验证方法 | 结果 |
| :--- | :--- | :--- | :--- |
| I1 | `current_stage` 只能在 7 个枚举值中 | 枚举校验 | 通过 |
| I2 | 任一投递的 `current_stage` 一次只能前进一格 | 连续 advance 测试 | 通过 |
| I3 | `revert` 后该阶段结果与时间戳被清空，`overall_status` 由 pass/fail 恢复为 pending | 撤回用例 | 通过 |
| I4 | 第一阶段不可再退 | 边界用例 | 通过 |
| I5 | 只有终面 pass 才使 `overall_status='pass'` | 路径覆盖 | 通过 |
| I6 | 已淘汰的投递经撤回后「复活」，且可继续推进 | 复活用例 | 通过 |
| I7 | `fromStage` 必须等于当前 `current_stage`，否则拒绝（防重复提交/并发双击） | 非法值用例 | 通过 |
| I8 | 撤回某阶段时，该阶段的 `reason`/`evaluation` 一并清空 | 关联清理用例 | 通过 |

> **I7 是亮点**：它是你系统里真实存在的乐观并发防护，写进论文就是「工程严谨性」；老师问「用户连点两次通过会怎样」时，这是标准答案。

### 3.3 L3：AI 筛选怎么评估（可落地的完整方案）

#### ① 建评估集（1～2 天）

- **规模**：100 份（50 份「应通过」+ 50 份「应淘汰」），少于 60 份统计意义不足，多于 150 份时间成本过高。
- **来源**：**绝对不能用实习公司的真实简历**。用两种合法来源：
  - 自己/同学构造的样例简历（脱敏虚构姓名、虚构项目经历）；
  - 公开简历数据集（如 Kaggle 上的 resume dataset）改写为中文。
- **标注**：每份给出 `人工结论`（pass/fail）+ `目标岗位`，标注者 1 人即可（你自己），但要**记录标注时间与依据**，并在论文里说明「单人标注」这一局限。

#### ② 选指标（写清楚为什么选它）

| 指标 | 公式 | 为什么要在论文里出现 |
| :--- | :--- | :--- |
| 准确率 Accuracy | (TP+TN)/N | 最直观，但正负样本均衡时才可靠 |
| 精确率 P | TP/(TP+FP) | **对招聘场景更重要**：误判通过的简历会浪费面试官时间 |
| 召回率 R | TP/(TP+FN) | 误判淘汰会漏掉人才，代价更大 |
| F1 | 2PR/(P+R) | 综合 |
| 一致性 Kappa | 与人工判断的 Cohen's κ | **最能体现「AI 能否替代人工初筛」**，>0.6 即可称「高度一致」 |
| 稳定性 | 同一简历 3 次运行结论一致率 | LLM 非确定性，必须测 |
| 时延/成本 | 单份平均耗时、平均 token | 工程价值 |

#### ③ 做消融（这是「研究感」的来源）

三组对比，同一评估集：

| 组 | 提示词配置 | 预期 |
| :--- | :--- | :--- |
| G1 基线 | 仅系统默认规则 | 准确率最低 |
| G2 自定义规则 | 默认规则 + 岗位筛选规则 | 提升 |
| G3 加附加条件 | G2 + 岗位级 AI 附加条件（如「必须有医疗行业经验」） | 精确率提升、召回可能下降 |

结论一句话：「提示词越具体，精确率越高但召回率下降，说明该方法的瓶颈在于**约束表达与误杀之间的权衡**，而非模型能力。」——**有这句话，你的第 6 章就不是测试报告，是研究结论**。

#### ④ 错误分析（必写，且极加分）

把 100 份里判错的挑出来分类，做成表：

| 错误类型 | 频次 | 典型表现 | 原因 | 改进方向 |
| :--- | :--- | :--- | :--- | :--- |
| 扫描件无法提取 | n | PyMuPDF 返回空/过短 | 图片型 PDF | OCR 前置 |
| 姓名识别错误 | n | 把「简历」当成姓名 | 版式不规范 | 二次校验/人工改名（你已有此功能） |
| 岗位错配 | n | 自动模式下硬凑岗位 | 提示词「宁可不匹配」约束不足 | 加置信度阈值 |
| 结论不可解析 | n | 返回散文而非 JSON | 模型不遵守格式 | 已有重试+严格格式（你已实现） |

**这张表的价值**：它证明你知道系统的边界在哪。答辩时被问「AI 会不会判错」，你直接翻到这页。

### 3.4 L2：测试用例表的规范写法

不要写「测试了导出功能，正常」。按这个格式，40 行左右：

| 编号 | 模块 | 前置条件 | 操作步骤 | 预期结果 | 实际 | 结论 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| TC-APP-07 | 投递 | 存在 pending 投递，当前 ai 阶段 | POST advance, fromStage=ai, result=pass | 200，stage→resume，写时间戳 | 一致 | 通过 |
| TC-APP-11 | 投递 | 同上传错 fromStage=phone | POST advance | 400 拒绝 | 一致 | 通过 |
| TC-STAT-04 | 统计 | 某岗位设为暂不招，其下有 3 条投递 | GET matrix | 该岗位列不出现，总计不含其人数 | 一致 | 通过 |
| TC-EXP-02 | 导出 | 选择 mode=report | POST /api/export | 返回 xlsx，含两个工作表 | 一致 | 通过 |

覆盖维度清单（照着勾）：**正常路径 / 边界值 / 非法输入 / 权限（无 token、过期 token）/ 数据一致性（统计与明细对账）/ 并发（连点两次）/ 空数据（全新账号）**。

### 3.5 RQ3 的口径验证：人工手算对照

交叉表是你系统里**最容易算错、也最容易被问倒**的地方。方法：

1. 造一个 20 条投递的小数据集，把「岗位、阶段、各关结果、时间戳、隐藏状态」列成表；
2. **手工**按你的口径定义算一遍交叉表；
3. 跑系统，逐格比对；
4. 差异逐条归因（时间戳边界、面试合并计数、隐藏岗位排除、撤回后的结果清空）。

在论文里写：「为验证统计口径，构造含 20 条投递、覆盖 4 种边界情形的小规模数据集，人工计算结果与系统输出完全一致（逐格比对，共 4×5=20 格）。」——**这一句话，含金量高于三页截图。**

## 4. 论文结构：每章的功能、字数与写法

默认按**本科 1.5～2 万字、6～7 章**设计。若你们学校定死了章数，按此映射调整。

| 章 | 功能 | 字数占比 | 必备图表 | 最常见错误 |
| :--- | :--- | :--- | :--- | :--- |
| 摘要 | 全文压缩（背景/方法/结果/结论） | 400～600 字 + 英文 | — | 写成目录复述，无量化结果 |
| 第1章 绪论 | 为什么做、别人做到哪、我要做什么 | 15% | 1 张研究内容框架图 | 背景空泛，现状=罗列 |
| 第2章 相关技术 | 技术依据与取舍 | 15% | 3～4 张对比表 | 抄官网 |
| 第3章 需求分析 | 要解决什么、验收标准 | 12% | 用例图、功能结构图 | 无量化非功能需求 |
| 第4章 系统设计 | 怎么设计、为什么这样设计 | 25% | 架构图、E-R、状态机、时序图 | 只有图没有论证 |
| 第5章 系统实现 | 难点怎么解决 | 20% | 关键界面、核心流程、代码片段 | 按页面罗列功能 |
| 第6章 测试与评估 | 对不对、准不准、能不能用 | 10% | 用例表、混淆矩阵、消融图 | 只写「测试通过」 |
| 第7章 总结与展望 | 结论、局限、未来 | 3% | — | 展望空话 |

### 4.1 摘要（最后写，但决定第一印象）

四句话模板：

1. **背景一句**：招聘流程的多阶段管理与简历初筛高度依赖人工，效率低且易漏。
2. **做了什么一句**：本文设计并实现了一个本地部署的个人招聘管理系统，包含 7 阶段可逆状态机、零训练 LLM 简历初筛、可下钻交叉统计与周报导出。
3. **怎么验证一句**：通过 72 项接口断言、8 条状态机不变量、100 份标注简历的评估验证，AI 初筛准确率达 XX%，F1 为 XX，单份平均耗时 X.X 秒。
4. **结论/价值一句**：结果表明，在无标注语料约束下，结构化约束提示词可达到与人工初筛 XX 的一致性，具备实用价值。

> 摘要里**必须有数字**。没有数字的摘要，老师扫一眼就归到「普通」档。

### 4.2 第 1 章 绪论：五段式

| 节 | 写什么 | 素材 | 陷阱 |
| :--- | :--- | :--- | :--- |
| 1.1 研究背景与意义 | 招聘数字化的行业趋势 → 人工流程的具体痛点 → 本课题的实践来源 | 参考文献清单第 1、2、10 条；你的实习观察（脱敏） | 大段抄政策文件 |
| 1.2 国内外研究现状 | 按「招聘系统 → 简历自动筛选 → 流程建模」三条线梳理，每条线落在「已有工作 + 局限」 | 清单第 2、4、13、17 条 | 只罗列不评价（必须每篇点出局限） |
| 1.3 研究内容与贡献 | 三条贡献（见 1.3 节模板） | RQ1-3 | 贡献写得像功能清单 |
| 1.4 论文组织结构 | 每章一句话 | — | 写「第2章介绍相关技术」这种目录复述（可接受，但一笔带过） |
| 1.5（可选）技术路线图 | 一张图说明全流程 | draw.io | 图与正文不符 |

**1.2 的写法示例**（这是最容易写差的节）：

> 已有研究可分为三类。**系统实现类**工作侧重功能完备性，如文献[3]实现的校园招聘系统覆盖了岗位发布与投递管理，但流程状态多为单向推进，缺乏对误操作与候选人回流的支持；**自动化筛选类**工作集中于提升匹配精度，文献[17]采用深度学习与谱聚类实现简历排序，取得了较好效果，但依赖标注语料与模型训练，难以在无标注的小规模场景中复用；**流程建模类**工作关注状态机与工作流引擎的正确性，但其面向的是审批、工单等场景，尚未与招聘业务的多阶段、可撤回特性结合。综上，如何在**无标注语料、单机部署**的约束下同时解决流程可逆建模与简历初筛，仍缺少系统性工作。

这段 300 字，包含 3 篇引用、3 个局限、1 个切入点——这就是合格的「研究现状」。

### 4.3 第 2 章 相关技术：比较 > 介绍

每节结构固定为：**是什么（2 句）→ 关键特性（3 点）→ 与本项目的关系 → 本项目为何选它（引选型表）**。

节次建议：2.1 前后端分离与 REST 架构 / 2.2 FastAPI 与异步处理 / 2.3 Vue 3 与组件化 / 2.4 MySQL 与数据建模 / 2.5 大语言模型与提示词工程 / 2.6 JWT 认证 / 2.7 本章小结。

**硬性要求**：每节至少一处引用；每节至少一句「本项目据此…」。

### 4.4 第 3 章 需求分析

- **功能需求**：不要按页面写，按**角色-场景**写。你只有「招聘专员」一个角色，就按 **7 个业务流程**写：登录认证 → 岗位维护 → 候选人建档 → 投递与推进 → AI 录入 → 汇总分析 → 导出。
- **非功能需求必须量化**（这是最容易被扣分的地方）：

| 类别 | 需求 | 指标 | 验证方式 |
| :--- | :--- | :--- | :--- |
| 性能 | 列表查询响应 | ≤ 500 ms（1 万条投递） | 计时 |
| 性能 | 单份简历 AI 判定 | ≤ 15 s | 计时 |
| 性能 | 周报导出 | ≤ 5 s（1 万行） | 计时 |
| 并发 | 批量录入 | 支持 10 份并发，互不阻塞 | asyncio 并发测试 |
| 安全 | 密码存储 | bcrypt 哈希，不存明文 | 查库验证 |
| 安全 | 接口鉴权 | 除登录/注册/健康检查外 100% 要求 Bearer Token | 无 token 调用全部接口 |
| 安全 | 隐私 | 简历 PDF 与提取文本不落盘 | 查库/查文件系统 |
| 可用性 | 中文本地化与主题 | 三档主题，刷新保持 | 手工验证 |
| 兼容性 | 浏览器 | Chrome/Edge 最新版 | 手工验证 |

- **用例图**：1 张，7 个用例，标注参与者（招聘专员）。
- **本章小结**：明确列出「验收标准」，直接对应第 6 章的测试用例——**首尾呼应**是加分项。

### 4.5 第 4 章 系统设计：论文的主体，占 25%

节次与必备图：

| 节 | 内容 | 图 |
| :--- | :--- | :--- |
| 4.1 总体架构设计 | 三层/分层架构，前端 SPA ↔ REST ↔ 服务层 ↔ ORM ↔ MySQL；横向切面：认证、AI、导出 | **图 4-1 系统总体架构图** |
| 4.2 功能模块设计 | 7 个模块的划分依据（按业务实体划分，不按页面） | 图 4-2 功能结构图 |
| 4.3 数据库设计 | 概念模型 → 逻辑模型 → 物理模型；6 张表；范式分析；索引与约束理由 | **图 4-3 E-R 图**（用 `ATS.pdm` 导出）、表 4-x 数据字典摘要 |

**4.4 的写法要点**：先给形式化定义——

> 定义 1（招聘状态机）：五元组 M = (S, Σ, δ, s₀, F)，其中 S = {ai, resume, phone, test, pro, hr, final, pass, fail}，Σ = {advance_pass, advance_fail, revert}，δ: S × Σ → S 为转移函数（见图 4-4），s₀ = ai，F = {pass, fail}。
>
> 定义 2（可逆性）：对任意 s ∈ S 与引起的转移，存在 revert 使其恢复至前一阶段并清除该阶段观测值，且撤回后 overall_status 回到 pending。

有了这两个定义，第 4.4 节就有了学术形态，而不再是「我画了个流程图」。

**4.6 的口径定义**必须写成文字规则（不能只画图）：

> 规则 1：格子 (岗位 p, 阶段 r) 的计数 = |{投递 a | a.position = p 且 a 在时间范围 T 内「通过 r」或「正停在 r」}|；
> 其中「通过 r」= 该阶段 result 为 pass 且该阶段时间戳 ∈ T；「正停在 r」= current_stage = r 且尚未给出该阶段结果，以 update_time ∈ T 判定。
> 规则 2：面试行只判专业面，避免同一人在三个面试环节被重复计数。
> 规则 3：is_hidden 岗位及其全部投递不参与任何统计与导出。

→ 这三条规则，就是可以被老师检验、被后来者复用的**知识产出**。

### 4.6 第 5 章 系统实现：按「难点」组织，不按「页面」组织

这是**最容易写崩的一章**。错误写法：5.1 登录页实现、5.2 岗位页实现……（= 说明书）。
正确写法：按**技术难点**组织，每节「难点 → 方案 → 关键代码 → 效果」。

建议 5 节：

| 节 | 难点 | 关键代码（≤20 行/段） | 效果证据 |
| :--- | :--- | :--- | :--- |
| 5.1 认证与请求链路 | token 注入、401 统一跳转 | axios 拦截器 + FastAPI 依赖注入 | 截图/时序 |
| 5.2 状态机实现 | 正向/逆向转移与结果清空的事务性 | advance/revert 服务函数 | 用例结果 |
| 5.3 AI 录入管线 | PDF 抽取 → 提示词构造 → 多配置轮询 → 容错解析 | 提示词模板片段 + 解析归一化函数 | 录入结果截图 |
| 5.4 交叉统计与下钻 | 口径实现、格子名单、时间范围 | 统计服务核心查询 | 交叉表 + 弹窗截图 |
| 5.5 周报导出 | 双工作表、列宽/表头样式、csv 退化 | openpyxl 写入片段 | 导出的 Excel 截图 |

**代码片段规范**：每段不超过 20 行，只贴**算法/逻辑核心**，不贴 import 和框架样板；每段前面用一句话说明「这段在解决什么」，后面用一句话说明「为什么这样写比另一种写法好」。

### 4.7 第 6 章 测试与评估

按第 3 节三级体系写：6.1 测试环境与方法 / 6.2 功能测试（用例表 40 行 + 不变量表 8 行）/ 6.3 接口测试（72 项断言）/ 6.4 **AI 初筛效果评估**（评估集、指标、消融、错误分析）/ 6.5 性能测试 / 6.6 安全性测试 / 6.7 本章小结。

**6.4 是整篇论文的分数分水岭。**

### 4.8 第 7 章 总结与展望

- 总结：三条贡献各一段，**每段带一个数字**。
- 局限（诚实写 4 条）：单用户无权限体系；简历初筛依赖外部 API 的稳定性与费用；无 OCR，扫描件支持有限；统计口径仅覆盖单一口径（未支持自定义指标）。
- 展望（对应局限，写 4 条，具体到技术）：引入 RBAC；本地小模型量化部署；OCR 前置；候选人邮件/短信通知与面试日程。

### 6.1 每日写作节奏（抗拖延）

- **2 小时写作法**：40 min 只写不查（不查资料、不查代码）→ 5 min 休息 → 40 min 补证据（插引用、补数字）→ 15 min 顺句。
- **每天只写一节**，写完就在目录上打勾。一节 800～1200 字。
- **卡住超过 20 分钟**就换一件小事做（画图、整理用例表、改格式），别硬耗。
- **写完不立刻改**。初稿当天的任务是「写完」，第二天再「写好」。

### 6.2 导师沟通节奏

每周一次，每次**带三个具体问题**，不要问「老师您看我写得怎么样」。正确问法：

- 「4.4 节的状态机我只给了转移表和两条定义，是否需要补形式化的正确性证明？」
- 「第 6 章的 AI 评估用 100 份自建样本、单人标注，这个规模老师认为够吗？」
- 「第 2 章我把 FastAPI 和 Django 做了对比表，是否偏工程、需要更学术的角度？」

### 6.3 如果只剩 4 周：降级方案（保留评估，砍功能叙述）

| 保留 | 砍掉 |
| :--- | :--- |
| 第 4 章设计图（5 张核心） | 第 2 章的技术罗列压缩为 1 节 |
| **AI 评估（60 份样本、单组指标即可）** | 消融对比降为一句话结论 |
| 状态机不变量表 | 用例表压缩到 20 行 |
| 交叉表口径三规则 | 性能测试只留 1 个指标 |

原则：**宁少一个功能，不少一个数字。**

## 7. 质量闸门与自检清单

### 7.1 每章完成后的 8 项检查

1. 本章能对应到哪个 RQ？（论点闸）

### 7.3 查重的正确姿势

- 查重系统一般**排除参考文献列表**，所以文献多不会推高重复率。

- 降重不是换同义词，而是**改变叙述结构**：把「FastAPI 支持异步」改成「本系统要求在同一请求内并发调度多个外部 API，因此框架需原生支持协程，FastAPI 满足该约束」。

## 8. 答辩方法论

### 8.1 PPT 12 页结构

| 页 | 内容 | 时间 |
| :--- | :--- | :--- |
| 1 | 封面（题目、姓名、导师） | 10 s |
| 2 | 研究背景与问题（一张痛点图） | 40 s |
| 3 | 研究现状与切入点（三条线各一句局限） | 40 s |
| 4 | 三个研究问题 + 三条贡献 | 40 s |
| 5 | 系统总体架构图 | 50 s |
| 6 | **核心一：7 阶段可逆状态机**（转移图 + 2 条不变量） | 60 s |
| 7 | **核心二：零训练 AI 初筛管线**（时序 + 提示词结构） | 60 s |
| 8 | **核心三：可下钻交叉统计与周报导出**（口径三规则） | 50 s |
| 9 | **评估结果**（混淆矩阵 + 指标表 + 消融图） | 70 s |
| 10 | 系统演示截图组（4 张） | 30 s |
| 11 | 局限与展望 | 30 s |
