# 部署与备份恢复（v3.15）

> 适用：本机 / 内网单机部署。三个端共用一套后端与一个 MySQL 库。
> 相关文档：[技术栈与开发计划](技术栈与开发计划.md)、[数据库字段说明](数据库字段说明文档.md)、[候选人端与管理端方案](候选人端与管理端方案.md)。

## 一、环境检查

| 依赖 | 版本 / 要求 |
| :--- | :--- |
| Python | 3.11 |
| MySQL | 8.x，`utf8mb4`，`max_allowed_packet ≥ 16M`（默认 64M 即可） |
| Node.js | 18+（当前开发环境 24） |
| 端口 | 后端 8000、前端 5173、MySQL 3306（只监听本机） |

`max_allowed_packet` 检查：

```sql
SHOW VARIABLES LIKE 'max_allowed_packet';
```

因为候选人文件以 `LONGBLOB` 存库，太小会导致 10MB 文件写入失败。

## 二、首次部署

```powershell
# 1. 建库并建表
mysql -u root -p -e "CREATE DATABASE IF NOT EXISTS ats DEFAULT CHARSET utf8mb4;"
mysql -u root -p ats < step/StepO/crebas.sql

# 2. 后端
cd ats\backend
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
copy .env.example .env
# 编辑 .env：DATABASE_URL 的密码、SECRET_KEY 换成随机值

# 3. 创建技术管理员（技术端 /tech 用）
.venv\Scripts\python scripts\create_user.py --role admin --username tech --password admin

# 4. 启动后端
.venv\Scripts\uvicorn app.main:app --host 127.0.0.1 --port 8000

# 5. 前端（另开窗口）
cd ..\frontend
npm install
npm run dev
```

访问：

| 端 | 地址 | 账号来源 |
| :--- | :--- | :--- |
| HR | `http://127.0.0.1:5173` | 自助注册，或技术端创建 |
| 候选人 | `http://127.0.0.1:5173/portal` | 手机号；账号由 HR 录入手机号后自动开通 |
| 技术管理 | `http://127.0.0.1:5173/tech/login` | 部署脚本 / 技术端创建 |

> 默认密码：候选人 `admin`；技术端与 HR 由创建时指定。**部署后请立即修改 `tech` 的密码。**

## 三、老库升级（v3.14 → v3.15）

```powershell
# 先备份
mysqldump -u root -p --single-transaction ats > backup_before_v3.15.sql

# 只加列 / 加表，不删数据
mysql -u root -p ats < step/StepO/migrate_v3.15_three_portal.sql

# 存量账号全部变成 hr；技术管理员另建
.venv\Scripts\python scripts\create_user.py --role admin --username tech --password admin
```

回滚（会丢弃 6 张新表与新增列，务必先备份）：

```powershell
mysql -u root -p ats < step/StepO/rollback_v3.15_three_portal.sql
```

## 四、备份

技术管理端 → `备份导出` → 下载 `ats_backup_YYYYmmdd_HHMMSS.zip`：

```
manifest.json          版本、时间、各表行数、文件数
csv/*.csv              12 张表（候选人文件表只含元数据）
files/{ID}_{文件名}      候选人文件原件
```

也可以命令行备份整库：

```powershell
mysqldump -u root -p --single-transaction --routines --triggers ats > ats_manual.sql
```

> 备份包含候选人个人信息、简历原件、密码哈希，只应保存在可信位置。

## 五、恢复（手工）

1. **停服务**：关闭前端、后端。
2. **恢复数据库结构**：
   - 新机器：执行 `crebas.sql`；
   - 同版本覆盖：先备份当前库，再按需导入。
3. **导入 CSV**：按 `Candidate → Position → User → Application → AI_API_Config → App_Setting → Candidate_File → Form_Template → Form_Field → Form_Submission → Form_Answer → Operation_Log` 的顺序导入；注意自增 ID 与外键。
4. **恢复文件**：把 `files/{ID}_{文件名}` 的二进制内容写回 `Candidate_File.Content`，`Original_Name` 用文件名去掉 `ID_` 前缀。
5. **校验**：登录三个端，检查岗位数、投递数、候选人文件、表单答卷；确认 `AI_API_Config` 中启用的配置可用。
6. 或者直接用 `mysqldump` 的 SQL 备份整库恢复（最快，但会覆盖当前库）。

## 六、日常维护

| 事项 | 做法 |
| :--- | :--- |
| 改 AI 模型 / 密钥 | 技术端 → 系统配置 |
| 改 AI 筛选规则 | 技术端 → 系统配置 → 提示词 |
| 新增 HR | 技术端 → 账号管理 |
| 候选人无法登录 | 检查候选人档案是否有手机号、账号是否停用 |
| 候选人看不到简历 | HR 在候选人详情上传简历 |
| 查看谁改了什么 | 技术端 → 操作日志 |
| 数据库变大 | 技术端看体积；备份后按需清理历史日志 / 文件 |

## 八、安全约定

- 所有服务只监听 `127.0.0.1`；不要直接暴露到公网。
- `.env`、数据库备份、AI 密钥、简历原件都不进 Git。
- 候选人只能访问自己的投递/文件/表单；技术管理员只能访问系统维护接口，不能浏览招聘业务数据。
- 三个端各有独立 token；同一浏览器可分别登录互不影响。
