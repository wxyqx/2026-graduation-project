# 三角色平台方案：候选人端 / HR 端 / 技术管理端（v3.15 草案 · 第 2 版）

> **实施进度**：阶段 0 ✅ 方案评审 · 阶段 1 ✅ 数据基座与三角色 · 阶段 2 ✅ 候选人账号与登录 · 阶段 3 ✅ 文件与可配置表单 · 阶段 4 ✅ 候选人投递与 AI 首筛 · 阶段 5 ✅ 候选人端前端 · 阶段 6 ✅ HR 端适配 · 阶段 7 ✅ 技术管理端 · 阶段 8 ✅ 联调、测试与文档（2026-10-24）· **v3.15 三角色平台交付**
>
> 截图：`step/StepO/screenshots/`（候选人端 375/1440；HR 端、技术端 1440）。
>
> 本版根据你的答复重写。**上一版的双端模型作废**，以本版为准。
>
> 已确认的前提：
> 1. 现有端是 **HR 用**的，保留为 HR 端；新增 **技术管理端**（公司技术人员用）与 **候选人端**。
> 2. 候选人账号来源 = **手机号**；手机号必须先在系统里存在（HR 录入或 AI 识别），候选人才可登录。
> 3. 默认密码统一 `admin`，**不强制改密**。
> 4. 候选人可以查看 HR 上传的简历/附件、填写可配置表单，HR 能看到这些内容；候选人**不需要也不能**自己上传简历。
> 5. 候选人可见：阶段 + 结果 + 时间 + 自己填的表单/文件；看不到内部评价与 AI 理由。
> 6. 候选人不能撤回投递。
> 7. 文件全部存放在**现有 MySQL 数据库**里（BLOB），不另起文件服务器。
> 8. 技术管理端职责：账号与权限、系统配置（AI/提示词）、操作日志、数据备份与导出、运行概览。
>
> 实施顺序：**先候选人端**（阶段 1–5），再做 HR 端适配（阶段 6），最后技术管理端（阶段 7）与收尾（阶段 8）。
> 每个阶段结束都会停下来交给你审核，通过后才进入下一阶段。

## 0. 结论先行

不改 7 关招聘状态机、AI 筛选、统计导出的业务内核，只在外面加三层「身份与入口」，并把「候选人提交物」补进数据模型：

```
                    ┌──────────────────────────────┐
                    │  MySQL 8（唯一数据库 ats）     │
                    └──────────────────────────────┘
                         ▲          ▲          ▲
        候选人端 /portal  │   HR端 /  │  技术管理端 /tech
        (手机号+admin)    │ (用户名)  │  (用户名)
                         │          │
  看岗位 / 传文件 / 填表  │ 招聘全流程 │ 账号/配置/日志/备份
  看自己的进度            │ 看候选人材料│ 不碰招聘业务数据
```

- 角色：`User.role ∈ {candidate, hr, admin}`。存量账号迁移为 `hr`；技术管理员由脚本创建。
- 候选人账号：`Candidate.phone` 一旦有值，系统自动开通 `User(role=candidate)`，默认密码 `admin`。
- 候选人提交物：`Candidate_File`（文件 BLOB）+ 可配置表单（`Form_Template` / `Form_Field` / `Form_Submission` / `Form_Answer`）。
- 三套 token、三套前端入口、三套路由守卫，互不越权。

## 1. 三个端分别做什么

### 1.1 候选人端（`/portal`，移动优先）

| 功能 | 说明 |
| :--- | :--- |
| 登录 | 手机号 + 密码（默认 `admin`）；手机号不在系统里 → 提示「未找到你的档案，请联系 HR」 |
| 岗位浏览 | 只显示在招岗位（`is_hidden=0`），可看 JD、负责人 |
| 投递 | 选岗位 → 确认/上传简历 → 填该岗位表单（若配置）→ 提交；触发 AI 首筛 |
| 我的投递 | 列表 + 7 关纵向时间线；只显示阶段、通过/淘汰、时间 |
| 我的文件 | 查看/下载 HR 上传的简历与附件（只读） |
| 我的表单 | 填写个人资料表 + 各投递对应岗位表；可保存草稿、提交、再次修改 |
| 我的资料 | 姓名/手机号只读，邮箱可改；可选改密（不强制） |

### 1.2 HR 端（现有 `/`，桌面）

保留全部现有功能：岗位、候选人、投递、7 关推进/撤回、各关原因与面试评价、AI 录入、面试评价、汇总导出、阶段文案设置。

新增/调整：

- 候选人档案增加 **手机号、邮箱、账号状态**（已开通/未开通）。
- 候选人详情增加 **文件**、**表单答卷** 两个分区，可下载原件。
- 新建/编辑候选人时可填手机号；填了即自动开通候选人账号。
- AI 智能录入自动识别简历中的手机号；识别不到时标记「待补手机号」。
- 投递列表增加「来源」（管理端 / AI录入 / 候选人自主投递）。
- 表单模板管理（HR 定义要问候选人的问题）。
- **移除**系统设置里的 AI 配置与提示词（移交给技术管理端），保留阶段文案改写。

### 1.3 技术管理端（`/tech`，桌面）

| 模块 | 内容 |
| :--- | :--- |
| 运行概览 | 账号数（HR/候选人）、岗位数、投递数、文件总大小、近 7 天登录与 AI 调用次数 |
| 账号与权限 | 创建/停用 HR 账号、重置密码；查看候选人账号状态、重置密码；管理员自己的账号 |
| 系统配置 | AI 接口配置（增删改、启用）、AI 筛选提示词；岗位字典/枚举说明（只读） |
| 操作日志 | 登录、改密、账号启停、文件上传删除、表单模板修改、导出、备份等 |
| 数据备份 | 导出全库 ZIP（CSV + 文件原件 + manifest）；恢复本期手工执行 |

> 技术管理端**不提供**候选人、投递、面试等业务数据的浏览入口（备份除外），避免技术人员日常接触候选人隐私。

## 3. 关键设计决策

| 编号 | 决策 | 结论 |
| :--- | :--- | :--- |
| D1 | 角色模型 | 三角色 `candidate / hr / admin`，一个 `User` 表 |
| D2 | 候选人账号来源 | `Candidate.phone` 唯一；有手机号即自动开通账号，无自助注册 |
| D3 | 默认密码 | `admin`，不强制改密；候选人可自愿改密 |
| D4 | 手机号必填性 | 候选人档案手机号可空（兼容存量），但**没有手机号就无法登录**；HR 会看到「待补手机号」 |
| D5 | 文件存储 | MySQL `LONGBLOB`，单文件 ≤ 10MB，单候选人 ≤ 50MB；不落磁盘 |
| D6 | 文件类型 | PDF / DOC / DOCX / JPG / PNG；下载时按原 MIME 返回，文件名清洗 |
| D7 | 表单配置者 | HR（业务侧定义要问什么）；技术管理端只提供入口与权限 |
| D8 | 表单绑定 | 全局「个人资料表」1 份 + 每个岗位可选 1 份「岗位申请表」 |
| D9 | 表单版本 | 模板改动 `version+1`，历史提交保原版本答案；候选人可修改后重新提交 |
| D10 | 候选人可见范围 | 阶段、结果、时间、自己的文件与表单；不返回 `*_reason`、`*_evaluation`、`ai_comment` |
| D11 | 撤回投递 | 不做 |
| D12 | AI 不可用 | 仍建投递，转 `pending_review` 人工筛 |
| D13 | 岗位可见 | 复用 `is_hidden=0`，不新增发布字段 |
| D14 | 存量账号 | 全部迁移为 `hr`；技术管理员用 `scripts/create_user.py --role admin` 创建 |
| D15 | HR 与管理员边界 | 技术管理员不能调用招聘业务接口；HR 不能调用技术管理接口 |
| D16 | AI 配置归属 | 系统级（只由管理员维护），不再按 User 隔离；`AiApiConfig.User_ID` 保留为「最后修改人」 |

## 4. 数据库设计（6 张既有表 + 6 张新表 = 12 张）

### 4.1 `User` 表

```sql
ALTER TABLE User
  MODIFY COLUMN username VARCHAR(50) NULL COMMENT 'HR/管理员用户名；候选人为 NULL',
  ADD COLUMN role VARCHAR(20) NOT NULL DEFAULT 'hr'
      COMMENT 'candidate=候选人 / hr=HR / admin=技术管理员',
  ADD COLUMN candidate_id INT NULL COMMENT '候选人账号关联的 Candidate.ID',
  ADD COLUMN is_active TINYINT NOT NULL DEFAULT 1 COMMENT '0=停用',
  ADD COLUMN last_login_time DATETIME NULL,
  ADD COLUMN last_login_ip VARCHAR(45) NULL,
  ADD COLUMN create_time DATETIME NULL COMMENT '若原表已有则跳过',
  ADD UNIQUE KEY UK_User_Candidate (candidate_id),
  ADD CONSTRAINT FK_User_Candidate FOREIGN KEY (candidate_id)
      REFERENCES Candidate (ID) ON DELETE SET NULL ON UPDATE RESTRICT;
```

- 存量用户 `role` 默认 `hr`。
- `username` 可空；MySQL 唯一索引允许多个 NULL，原 `AK_Username_UK` 保留。
- 候选人账号的 `username` 为空，登录走手机号；也可选择写入手机号，便于排查（本方案写入手机号，唯一约束天然防重）。

### 4.2 `Candidate` 表

```sql
ALTER TABLE Candidate
  ADD COLUMN phone VARCHAR(20) NULL COMMENT '手机号：候选人端登录账号，唯一',
  ADD COLUMN email VARCHAR(100) NULL,
  ADD COLUMN update_time DATETIME NULL,
  ADD UNIQUE KEY UK_Candidate_Phone (phone);
```

手机号规则：`^1[3-9]\d{9}$`；写入前去空格、去 `+86` 前缀；重复返回 409 并指出已存在的候选人。

### 4.3 `Application` 表

```sql
ALTER TABLE Application
  ADD COLUMN source VARCHAR(20) NOT NULL DEFAULT 'admin'
      COMMENT 'admin=HR手动 / ai_intake=AI录入 / portal=候选人自主投递';
```

### 4.4 `Candidate_File`（候选人文件，BLOB 入库）

```sql
CREATE TABLE Candidate_File (
  ID                INT NOT NULL AUTO_INCREMENT,
  Candidate_ID      INT NOT NULL COMMENT '所属候选人',
  Application_ID    INT NULL COMMENT '若绑定某次投递则填，个人文件为 NULL',
  Category          VARCHAR(20) NOT NULL COMMENT 'resume=简历 / certificate=证书 / portfolio=作品 / other=其他',
  Original_Name     VARCHAR(255) NOT NULL COMMENT '原始文件名',
  Mime_Type         VARCHAR(100) NOT NULL COMMENT 'MIME 类型',
  Size_Bytes        INT NOT NULL COMMENT '字节数，≤10MB',
  Content           LONGBLOB NOT NULL COMMENT '文件内容',
  Is_Current        TINYINT NOT NULL DEFAULT 1 COMMENT '1=当前版本；替换后旧版本置 0',
  Uploaded_By_Role  VARCHAR(20) NOT NULL COMMENT 'candidate / hr',
  Upload_Time       DATETIME NOT NULL,
  PRIMARY KEY (ID),
  KEY IX_Cand_Cat_Current (Candidate_ID, Category, Is_Current),
  KEY IX_File_App (Application_ID),
  CONSTRAINT FK_File_Candidate FOREIGN KEY (Candidate_ID) REFERENCES Candidate (ID)
      ON DELETE CASCADE ON UPDATE RESTRICT,
  CONSTRAINT FK_File_Application FOREIGN KEY (Application_ID) REFERENCES Application (ID)
      ON DELETE SET NULL ON UPDATE RESTRICT
);
```

说明：
- 删除候选人时文件随 `CASCADE` 删除。
- 替换简历：旧记录 `Is_Current=0` 保留历史，新记录 `Is_Current=1`。
- **`max_allowed_packet` 必须 ≥ 16M**（MySQL 8 默认 64M，需在部署检查项里确认），否则 10MB 文件会写入失败。

### 4.5 表单四表

```sql
CREATE TABLE Form_Template (
  ID           INT NOT NULL AUTO_INCREMENT,
  Name         VARCHAR(100) NOT NULL COMMENT '模板名，如「候选人资料表」「Java岗申请表」',
  Scope        VARCHAR(20) NOT NULL COMMENT 'profile=个人资料表 / position=岗位申请表',
  Position_ID  INT NULL COMMENT 'Scope=position 时必填',
  Description  VARCHAR(500) NULL,
  Version      INT NOT NULL DEFAULT 1 COMMENT '字段变更时 +1',
  Is_Active    TINYINT NOT NULL DEFAULT 1 COMMENT '0=停用，候选人不再看到',
  Created_By   INT NULL COMMENT '创建人 User.ID',
  Create_Time  DATETIME NOT NULL,
  Update_Time  DATETIME NOT NULL,
  PRIMARY KEY (ID),
  KEY IX_Form_Scope (Scope, Position_ID, Is_Active),
  CONSTRAINT FK_Form_Position FOREIGN KEY (Position_ID) REFERENCES Position (ID)
      ON DELETE CASCADE ON UPDATE RESTRICT
);

CREATE TABLE Form_Field (
  ID           INT NOT NULL AUTO_INCREMENT,
  Template_ID  INT NOT NULL,
  Field_Key    VARCHAR(50) NOT NULL COMMENT '英文键，同一模板内唯一，如 education',
  Label        VARCHAR(100) NOT NULL COMMENT '显示名，如「最高学历」',
  Field_Type   VARCHAR(20) NOT NULL COMMENT 'text/textarea/number/date/daterange/select/radio/checkbox/email/phone/section/color',
  Required     TINYINT NOT NULL DEFAULT 0,
  Options_JSON TEXT NULL COMMENT 'select/radio/checkbox 的选项，JSON 数组',
  Placeholder  VARCHAR(200) NULL,
  Help_Text    VARCHAR(500) NULL,
  Max_Length   INT NULL,
  Sort_Order   INT NOT NULL DEFAULT 0,
  Is_Active    TINYINT NOT NULL DEFAULT 1 COMMENT '0=软删除，历史答案保留',
  PRIMARY KEY (ID),
  UNIQUE KEY UK_Form_Field_Key (Template_ID, Field_Key),
  CONSTRAINT FK_Field_Template FOREIGN KEY (Template_ID) REFERENCES Form_Template (ID)
      ON DELETE CASCADE ON UPDATE RESTRICT
);

CREATE TABLE Form_Submission (
  ID            INT NOT NULL AUTO_INCREMENT,
  Template_ID   INT NOT NULL,
  Candidate_ID  INT NOT NULL,
  Application_ID INT NULL COMMENT 'profile 表为 NULL；position 表填对应投递',
  Template_Version INT NOT NULL COMMENT '提交时的模板版本',
  Status        VARCHAR(20) NOT NULL DEFAULT 'draft' COMMENT 'draft=草稿 / submitted=已提交',
  Submit_Time   DATETIME NULL,
  Update_Time   DATETIME NOT NULL,
  PRIMARY KEY (ID),
  KEY IX_Sub_Candidate (Candidate_ID, Template_ID),
  KEY IX_Sub_Application (Application_ID),
  CONSTRAINT FK_Sub_Template FOREIGN KEY (Template_ID) REFERENCES Form_Template (ID)
      ON DELETE RESTRICT ON UPDATE RESTRICT,
  CONSTRAINT FK_Sub_Candidate FOREIGN KEY (Candidate_ID) REFERENCES Candidate (ID)
      ON DELETE CASCADE ON UPDATE RESTRICT,
  CONSTRAINT FK_Sub_Application FOREIGN KEY (Application_ID) REFERENCES Application (ID)
      ON DELETE CASCADE ON UPDATE RESTRICT
);

CREATE TABLE Form_Answer (
  ID             INT NOT NULL AUTO_INCREMENT,
  Submission_ID  INT NOT NULL,
  Field_ID       INT NOT NULL,
  Field_Key      VARCHAR(50) NOT NULL COMMENT '快照，字段删除后仍可读',
  Value_Text     TEXT NULL COMMENT '统一存文本；多选存 JSON 数组',
  PRIMARY KEY (ID),
  UNIQUE KEY UK_Answer_Field (Submission_ID, Field_ID),
  CONSTRAINT FK_Answer_Submission FOREIGN KEY (Submission_ID) REFERENCES Form_Submission (ID)
      ON DELETE CASCADE ON UPDATE RESTRICT,
  CONSTRAINT FK_Answer_Field FOREIGN KEY (Field_ID) REFERENCES Form_Field (ID)
      ON DELETE CASCADE ON UPDATE RESTRICT
);
```

唯一性规则（应用层保证）：
- 个人资料表：同一候选人同一模板只有一份 submission（`Application_ID IS NULL`）。
- 岗位申请表：同一投递同一模板只有一份。
- 模板停用后，已有 submission 仍可查看；候选人不再看到入口。

## 5. 权限模型

### 5.1 角色与入口

| 角色 | 登录方式 | 入口 | 可访问 |
| :--- | :--- | :--- | :--- |
| `candidate` | 手机号 + 密码 | `/portal/login` | `/api/portal/**` |
| `hr` | 用户名 + 密码 | `/login` | `/api/**`（招聘业务）+ `/api/hr/**` |
| `admin` | 用户名 + 密码 | `/tech/login` | `/api/tech/**` |

### 5.2 依赖

```python
get_current_user          # 验 token + 查库 + is_active
get_current_hr            # role == "hr"
get_current_candidate     # role == "candidate"
get_current_admin         # role == "admin"
```

- 未登录/token 失效 → 401，前端跳各自登录页。
- 角色不符 → 403「无权访问」，不跳登录。
- 停用 → 403「账号已停用」。

### 5.3 权限矩阵

| 接口组 | 候选人 | HR | 技术管理员 |
| :--- | :---: | :---: | :---: |
| `/api/auth/login`（HR） | ✗ | ✓ | ✗ |
| `/api/portal/auth/login` | ✓ | ✗ | ✗ |
| `/api/tech/auth/login` | ✗ | ✗ | ✓ |
| `/api/positions|candidates|applications|ai-screen|interview|stats|export` | ✗ | ✓ | ✗ |
| `/api/form-templates`（HR 配置） | ✗ | ✓ | ✗ |
| `/api/portal/**` | ✓ | ✗ | ✗ |
| `/api/tech/accounts|logs|backup|overview` | ✗ | ✗ | ✓ |
| `/api/tech/ai-configs|ai-prompt` | ✗ | ✗ | ✓ |
| `/api/health` | ✓ | ✓ | ✓ |

### 5.4 越权防护

1. 候选人所有查询都从 token 推导 `candidate_id`，不接受前端传 `can_id`。
2. 访问他人投递/文件/表单 → **404**（不暴露存在性）。
3. 候选人响应白名单序列化（`services/portal_views.py`），不带内部字段。
4. HR 接口不接受 `role` 参数，角色只由 token 决定。
5. 技术管理员调招聘业务接口 → 403；HR 调技术管理接口 → 403。
6. 文件下载单独鉴权：候选人只能下自己的；HR 可下全部；技术管理员不可下候选人文件。

投递流程：

```
1. 角色/账号状态校验
2. 岗位存在且 is_hidden=0
3. 必须有当前版本简历（Candidate_File 里 Category=resume 且 Is_Current=1）
4. 若配置了「个人资料表」且未提交 → 400「请先完善个人资料表」
   （岗位申请表不阻塞投递：投递成功后再补填，HR 看到「待补充」）
5. 查重 UK_Can_Pos → 409
6. 频控 24h ≤ 10 次
7. 读简历 → PyMuPDF 抽文本（扫描件抽不出也继续，降级人工）
8. AI 筛选（固定岗位）：
     成功 → ai_result + ai_comment，apply_result 推进
     失败/无配置/解析不了 → 降级 pending_review，投递不丢
9. 写 Application(source='portal')
10. 返回 screening 三态
```

> 设计调整（阶段 4 落地时确认）：原方案要求「岗位申请表提交后才能投递」，但岗位表需要 application_id 才能填，
> 会形成先有鸡还是先有蛋。现改为**投递后再补填岗位表**，个人资料表仍在投递前强制。

## 11. 风险登记表

| 编号 | 风险 | 影响 | 对策 |
| :--- | :--- | :--- | :--- |
| R1 | 手机号是账号唯一来源，存量候选人没有手机号 | 大量候选人无法登录 | HR 端筛「待补手机号」；AI 录入识别手机号；支持 HR 批量补录（阶段 6 可加） |
| R2 | AI 识别手机号不准 | 账号绑错人 | 手机号做格式校验；与已有手机号冲突时不覆盖；HR 可改 |
| R3 | 同名候选人 | 账号串数据 | 登录按手机号；AI 录入按手机号优先；同名且手机号不同则新建并标「待合并」 |
| R4 | BLOB 入库 | 库体积大、备份慢、`max_allowed_packet` 限制 | 单文件 10MB、单候选人 50MB；部署检查 64M；备份按需导出 |
| R5 | 可配置表单复杂度 | 工期膨胀 | 只做 12 种字段 + 排序 + 必填；不做条件联动、审批流、附件字段（文件独立） |
| R6 | 三端前端工作量 | 延期 | 先候选人端；HR 复用现有组件；技术端只做 5 页 |
| R7 | 三角色越权 | 数据泄露 | 统一依赖 + 3×3 矩阵测试 + 白名单序列化 |
| R8 | 默认密码 `admin` | 演示环境弱口令 | 不强制改密（按你的要求）；技术端可停用账号；文档注明仅本地演示 |
| R9 | 操作日志写失败影响主流程 | 业务报错 | 日志写入 try/except，失败只记应用日志 |
| R10 | 备份 ZIP 过大 | 下载超时 | 分批/流式写；前端提示预计大小；超过 200MB 建议停机备份 |
| R11 | 迁移改 `username` 可空 | 老代码异常 | 副本演练 + 回滚脚本 + 全量 smoke |
| R12 | HR 与管理员职责交叉 | 权限混乱 | 技术端不提供业务数据页；AI 配置迁移后 HR 端彻底移除 |
